# TextNavigator

Прототип для специалиста по закупкам: по загруженным TXT-документам восстанавливает
**действующие** условия поставок по состоянию на дату проверки и показывает проверяемое
основание для каждой суммы и каждого срока.

Приложение работает полностью в браузере: ни сервера, ни базы, ни внешних API. Загруженный
текст никуда не отправляется.

## Требования

- Node.js 20 или новее (разработка велась на Node 22)
- npm

## Установка и запуск

```bash
npm install
npm run dev
```

Откройте http://localhost:3000.

| Команда | Назначение |
| --- | --- |
| `npm run dev` | Дев-сервер |
| `npm run build` | Продакшн-сборка |
| `npm start` | Запуск собранной версии |
| `npm test` | Тесты парсера (Vitest) |
| `npm run lint` | ESLint |

### Зависимости

`next`, `react`, `react-dom`, `tailwindcss` (v4) — рантайм. `typescript`, `vitest`,
`eslint` — разработка. Больше ничего не подключено намеренно.

## Как пользоваться

1. Перетащите TXT-файлы в область загрузки или нажмите «Выбрать файлы».
2. Появится реестр: по строке на договор, блок «Быстрые ответы» и отдельный список
   несогласованных предложений.
3. Нажмите на **сумму**, **срок** или **ответ** — откроется панель обоснования: имя файла,
   вид и статус документа, точная цитата, абзац источника и правило, по которому получено
   значение. Там же — раздел «Связанные документы» со всеми документами этого договора.
4. Измените **дату проверки** — реестр пересчитается без повторной загрузки файлов.

### Проверочный пример

Учебные документы лежат в папке `documents`. Все шесть файлов при дате проверки
**10.03.2026** дают такой результат:

| Договор | Поставщик | Сумма, ₽ | Срок поставки | Несогласованные изменения |
| --- | --- | --- | --- | --- |
| STN-101 | ООО «Вектор Прибор» | 1 380 000 | 30.04.2026 | 2 |
| STN-102 | ООО «Контур Электро» | 840 000 | 20.03.2026 | 1 |
| STN-103 | ООО «ПромСнаб Сервис» | нет данных | 30.04.2026 | 0 |

Ответы на вопросы пользователя:

| № | Вопрос | Ответ |
| --- | --- | --- |
| 1 | Срок поставки по STN-101 на 10.03.2026 | 30.04.2026 |
| 2 | Сумма договора STN-102 | 840 000 ₽ |
| 3 | Сумма договора STN-103 | нет данных |
| 4 | Поставка раньше 01.04.2026 | STN-102 (20.03.2026); несогласованные изменения срока — STN-101 и STN-102 |

## Как принимается решение о приоритете

Условия изменяет **только подписанное сторонами допсоглашение, вступившее в силу к дате
проверки**. Если подписанных допсоглашений несколько, действует то, у которого позже дата
вступления в силу.

| Документ | Как учитывается |
| --- | --- |
| Договор, подписан | База для условий |
| Допсоглашение, подписан и вступил в силу ≤ даты проверки | Изменяет условия |
| Допсоглашение, подписан, но вступает в силу позже даты проверки | Только сведения: «Требуется проверка» |
| Проект допсоглашения, не подписан | Только сведения |
| Письмо поставщика | Только предложение |

Ничего не выводится из имени файла или порядка загрузки. Вид документа определяется по его
заголовку, номер договора — по содержанию, значения — по пунктам. Переименование файлов и
изменение порядка загрузки результат не меняют.

Если значение в тексте отсутствует, показывается **«нет данных»** с пояснением причины —
например, у STN-103 стоимость определяется спецификацией в приложении № 1, которого нет в
комплекте. Цифра `600 000 ₽` из этого договора — лимит закупки по внутреннему бюджету, прямо
оговорённый как не являющийся согласованной стоимостью, поэтому она не подставляется.

Несогласованные предложения не отбрасываются: они видны в разделе «Предложенные /
несогласованные изменения», а в строке договора появляется счётчик. Когда ситуацию не удалось
разрешить надёжно, выводится панель **«Требуется проверка»**.

### Заведомо отсекаемые значения

Парсер намеренно не принимает близкие по смыслу числа:

- авансовый платёж («входит в общую стоимость») — не итоговая сумма;
- лимит закупки / внутренний бюджет («не является согласованной стоимостью») — не сумма договора;
- срок оплаты («является сроком оплаты, а не поставки») и дата приёмки — не срок поставки;
- ставка неустойки — не сумма.

## Архитектура

```
documents/                 Учебные TXT-файлы
src/lib/types.ts           Общий контракт: доменные типы и сигнатуры точек входа
src/lib/parse/
  classify.ts              Вид документа, статус, ссылка на договор, номер
  extract.ts               Сумма, срок, поставщик, даты, разбиение на абзацы
  resolve.ts               analyzeDocuments(): база + подписанные допсоглашения в силе
  questions.ts             answerQuestions(): ответы на четыре вопроса
  index.ts                 Публичный API
src/app/                   Оболочка Next.js App Router (страница, layout, стили)
src/components/            Загрузка, таблица, вопросы, предложения, панель обоснования
```

Поток данных односторонний:

```
файлы (.txt) → classify → extract → resolve → analyzeDocuments()
                                                    ├→ таблица договоров
                                                    └→ answerQuestions() → четыре ответа
                                                              ↓
                                                    Provenance → панель обоснования
```

В компонентах нет логики разбора. Интерфейс вызывает `analyzeDocuments(files, checkDate)` и
`answerQuestions(result, checkDate)` и отображает результат — поэтому правила проверяются
тестами без браузера.

## Тесты

```bash
npm test
```

Набор загружает документы из `documents/` и проверяет:

- ожидаемую таблицу и ответы на четыре вопроса;
- независимость от имён файлов и порядка загрузки;
- что каждая цитата — реальная подстрока исходного файла и указывает на существующий абзац;
- что цитата — только решающий пункт и никогда не содержит числа аванса, лимита или срока оплаты;
- что `600000`, `252000` и `10.04.2026` не попадают в действующие условия;
- что снятие подписи с допсоглашения по STN-101 возвращает договор к `1 200 000 ₽` / `15.04.2026`
  и переводит допсоглашение в несогласованные.

# Записка

## Для кого прототип

Специалист по закупкам, который сверяет условия поставок по нескольким договорам и не хочет
перечитывать весь комплект документов заново. Его задача — быстро получить актуальные сумму и
срок на дату проверки **и иметь возможность доказать каждую цифру** ссылкой на источник,
потому что цена ошибки — неверный платёж или пропущенный срок.

## Пять вопросов клиенту

1. Писем от поставщика и проектов допсоглашений может быть много одновременно — нужно ли
   показывать их историю по дате или достаточно последнего предложения по каждому полю?
2. Считается ли допсоглашение вступившим в силу по дате подписания, если в тексте указана
   отдельная дата вступления в силу, и какая из них приоритетна при расхождении?
3. Бывают ли в вашем комплекте условия, которые заданы не в тексте, а в приложениях
   (спецификациях), и должны ли такие документы загружаться в систему?
4. Нужно ли сохранять результат проверки между сессиями и нужна ли выгрузка реестра
   (Excel/CSV) для передачи в бухгалтерию?
5. Кто именно должен видеть отметку «требуется проверка» — только закупщик или уведомление
   нужно направлять ответственному юристу?

## Принятые допущения

- Документы — текстовые файлы на русском языке, структурированные как предоставленный
  комплект: заголовок, `Дата:`, `Статус:`, нумерованные пункты.
- Дата проверки по умолчанию — **10.03.2026**; её можно изменить в шапке.
- Граница в четвёртом вопросе — первое число месяца, следующего за датой проверки (для
  даты по умолчанию это «раньше 01.04.2026»).
- Словосочетание «нет данных» выводится дословно, как требует задание.
- Один договор — один файл.
- Расчёты не выполняются: берётся указанная в договоре итоговая сумма; сумма, которую нужно
  собирать из цен и количеств, не вычисляется.
- Если два подписанных допсоглашения меняют одно поле, побеждает то, у которого позже дата
  вступления в силу; других сигналов приоритета нет.

## Две метрики полезности

1. **Точность извлечения на контрольном наборе.** Доля полей (сумма и срок по каждому
   договору), совпавших с эталоном, и доля неверных подстановок (аванс, лимит, срок оплаты)
   — целевое значение 0. Сейчас измеряется автоматическим тестом на 6 документах.
2. **Время до ответа на вопрос.** Сколько требуется от загрузки комплекта до готового ответа
   на четыре вопроса, по сравнению с ручным чтением. Сейчас это секунды и один экран.

Дополнительно можно считать долю значений, помеченных «нет данных», которые пользователь
счёл обоснованными: это показывает, не слишком ли осторожно система отказывается от догадок.

## Ключевые технические решения

1. **Правила и поиск вместо LLM внутри приложения.** Разбор построен на правилах: заголовок
   определяет вид документа, статус влияет на приоритет, значения извлекаются из конкретных
   пунктов. *Почему:* результат детерминирован, воспроизводим, объясним и укладывается в
   требование «нет платных API». *Компромисс:* правила заточены под этот формат документов и
   не поймут свободную формулировку, которую с ходу поймёт языковая модель. Границы
   применимости: типовой структурированный договор поставки; для иной формы потребуются новые
   шаблоны. При этом архитектура готова к тому, чтобы добавить LLM как вспомогательный
   разборщик для непонятных фрагментов, не меняя правила приоритета.
2. **Жёсткое разделение «движок разбора» и «интерфейс».** `analyzeDocuments()` и
   `answerQuestions()` — единственная точка входа; в компонентах нет логики разбора.
   *Почему:* правила проверяются тестами без браузера, а интерфейс можно менять, не боясь
   сломать расчёты. *Компромисс:* нужен явный контракт типов и лишний слой передачи данных.
3. **Приоритет определяется статусом и датой вступления в силу, а не именем файла.**
   *Почему:* прямое требование задания; имена файлов и дата загрузки не влияют ни на что.
   *Компромисс:* если в документе не указана дата вступления в силу, применить его нельзя —
   такой документ честно уходит в «требуется проверка», а не применяется «на глаз».

## Что изменится при 100 000 документов и наличии прав доступа

Сейчас весь разбор идёт в браузере в одном потоке, а состояние живёт до перезагрузки страницы.
На объёме в 100 000 документов это неприменимо по трём причинам, и каждая требует отдельного
решения:

- **Хранение и поиск.** Разбор в памяти → индекс (PostgreSQL + полнотекстовый поиск, либо
  отдельный поисковый движок) и хранение извлечённых полей как данных, а не как результата
  разбора «на лету». Нужны инкрементальный разбор и очередь на новые документы.
- **Производительность.** Один поток → разбор в Web Worker для больших файлов и серверная
  пакетная обработка для массовой загрузки; кэширование результата по хешу содержимого.
- **Права доступа.** Одно общее пространство → разграничение по организации и договору,
  потому что суммы и условия нельзя показывать всем. Обоснование при этом должно уважать права:
  цитата из документа, к которому у пользователя нет доступа, показываться не должна.
  Соответственно, список «связанных документов» тоже фильтруется по правам.

Появится и то, что сейчас не нужно: журнал изменений (кто и когда видел/подтвердил условие),
версионирование дополнений и уведомления об изменениях.

## Три следующих улучшения по приоритету

1. **Надёжное разрешение конфликтов и явный статус неопределённости.** Расширить правила:
   несколько допсоглашений на одно поле, отсутствующая дата вступления в силу, противоречия
   между документами — и показывать пользователю конкретный вопрос, требующий решения.
2. **Учёт приложений и спецификаций.** Закрыть случай STN-103: если стоимость определяется
   приложением, позволить загрузить это приложение и связать его с договором, чтобы «нет
   данных» превращалось в значение из источника.
3. **Экспорт и сохранение.** Выгрузка реестра в CSV/Excel и сохранение результата проверки,
   чтобы результат можно было передать дальше и сравнить с предыдущей сверкой.

# Отчёт о вайбкодинге

**Инструмент.** OpenCode: ведущий агент (`build`) плюс два субагента с чистой контекстной
областью — один на движок разбора, второй на интерфейс. Модель — DeepSeek V4.1 Flash через
OpenRouter. Агенты писали код, тесты и локализацию; я формулировал задания, принимал результат
и проверял его.

**Рабочий приём.** Работа разбита на два этапа с замороженным контрактом между ними: сначала
`src/lib/types.ts` и движок разбора с тестами, потом интерфейс, который может только читать
готовый результат. Тесты я запускал сам, а не полагался на отчёт субагента.

### Характерные запросы

1. Задание на движок разбора: перечислить ловушки комплекта как ожидаемый результат
   (STN-101 — 1 380 000 и 30.04.2026; STN-102 — 840 000 и 20.03.2026, а не аванс 252 000 и не
   срок оплаты 10.04.2026; STN-103 — «нет данных», а не лимит 600 000) и потребовать тест,
   доказывающий независимость от имён файлов.
2. Задание на интерфейс: контракт заморожен, «логики разбора в компонентах быть не должно»,
   всякий показанный значение обязано открывать основание с точной цитатой.
3. Задание на локализацию: точный словарь терминов («Требуется проверка», «нет данных»,
   «Допсоглашение»), таблица соответствия бейджей и требование корректных русских форм
   множественного числа (1 договор / 2 договора / 5 договоров).

### Пример неудачного решения ИИ и как оно было найдено

Движок разбора отчитался «зелёным»: тесты проходили, значения были верны. Но когда я вывел
реальный результат работы на комплекте, оказалось, что поле «точная цитата» содержит **весь
абзац целиком**, а не решающий пункт:

```
quote == paragraph  →  true
цитата: "2.1. Общая стоимость поставки составляет 1 200 000 ... НДС.
         2.2. Оплата производится в течение 20 календарных дней ..."
```

То есть в качестве обоснования суммы показывался в том числе пункт про оплату — именно то,
что задание запрещает смешивать. Формально требование «цитата должна быть подстрокой исходного
текста» выполнялось, поэтому тест это пропускал.

**Как проверял и исправлял.** Я не доверился отчёту, а выгрузил фактический результат и
сравнил поля. Причина нашлась в одном месте: в `resolve.ts` точная цитата, которую уже
вычислял `extract.ts`, затиралась абзацем. Я протянул решающий пункт до конца цепочки и
добавил тест, который прямо запрещает попадание в цитату чисел `252 000`, `600 000`,
`10.04.2026` и слов «Авансов», «Оплата». После правки цитата стала такой:

```
"Общая стоимость поставки составляет 1 200 000 (один миллион двести тысяч) рублей, включая НДС."
```

Вторая ошибка того же рода: тесты читали документы из соседней папки монорепозитория
(`../testDocs`), поэтому в **склонированном репозитории `npm test` падал**. Обнаружилось только
тем, что я клонировал репозиторий в чистую папку и прогнал `npm ci && npm test`. Исправлено:
документы переехали в `documents/` внутри проекта.

Оба случая — одна и та же закономерность: отчёт «всё зелёное» подтверждает только то, что
проверяли. Поэтому обязательными шагами стали независимый прогон тестов, выгрузка реальных
данных и проверка в браузере, а не чтение отчёта.

## Известные ограничения и заглушки

- Только TXT. PDF, DOCX и сканы не поддерживаются, OCR нет.
- Разбор опирается на формулировки этого комплекта. Ключевые слова и шаблоны пунктов собраны
  в `src/lib/parse/extract.ts`; иная формулировка потребует новых шаблонов.
- Итоговая сумма берётся из текста договора. Суммы, собираемые арифметически
  (цена × количество, прайс-листы), не вычисляются.
- Срок поставки распознаётся по конструкциям вида «не позднее ДД.ММ.ГГГГ» и «срок поставки».
  Относительные сроки («в течение 30 дней с даты подписания») не разрешаются.
- Поддерживаются только суммы в рублях.
- Словосочетание «нет данных» выводится дословно по требованию задания, остальной интерфейс —
  на русском.
- Результат не сохраняется: перезагрузка страницы очищает загрузку. Хранилища и экспорта нет.
- Секретов и ключей в коде нет; приложение не обращается к внешним сервисам.
